# AVL Trees

## Overview
AVL Trees, named after their inventors Adelson-Velsky and Landis, are a special type of self-balancing Binary Search Tree (BST). The "self-balancing" aspect is crucial: it means that the tree automatically adjusts its structure to maintain a certain height balance after every insertion or deletion operation. This ensures that the tree never becomes too "skewed" or lopsided, which is a common problem with regular BSTs.

The core idea behind an AVL tree is to maintain a property called the "height balance" for every node. For any node in an AVL tree, the difference in height between its left and right subtrees (known as the balance factor) must be -1, 0, or 1. If this property is violated after an operation, the tree performs specific rotations to restore balance. This strict balance guarantee ensures that operations like search, insertion, and deletion always complete in logarithmic time, $O(\log n)$, where $n$ is the number of nodes in the tree.

## What Problem It Solves
Regular Binary Search Trees (BSTs) offer efficient average-case performance for search, insertion, and deletion operations, typically $O(\log n)$. However, their worst-case performance can degrade significantly. If elements are inserted into a BST in a sorted (ascending or descending) order, or in a near-sorted order, the tree can become completely unbalanced, resembling a linked list. In such a "skewed" tree, the height of the tree becomes $O(n)$, and consequently, all operations (search, insert, delete) also degrade to $O(n)$ time complexity. This linear time complexity is unacceptable for large datasets, as it can lead to very slow processing times and make the system impractical.

**The core problems AVL Trees solve are:**
1.  **Worst-Case Performance Degradation:** By guaranteeing a balanced structure, AVL trees eliminate the worst-case $O(n)$ time complexity of BST operations, ensuring consistent $O(\log n)$ performance regardless of the input data order.
2.  **Unpredictable Performance:** In applications where consistent and predictable performance is critical, a regular BST's varying performance based on input sequence is a major drawback. AVL trees provide this predictability.
3.  **Inefficient Data Retrieval:** For large datasets, an $O(n)$ search can mean iterating through millions of elements, which is highly inefficient. AVL trees ensure that data can always be retrieved quickly.

**Why is it needed in machine learning?**
While AVL trees are not machine learning algorithms themselves, they are fundamental data structures that underpin many efficient systems and algorithms, including those used in machine learning:
*   **Efficient Data Management:** ML models often deal with vast amounts of data. Efficient storage and retrieval of features, labels, or intermediate results are crucial. AVL trees can be used to build high-performance in-memory databases or indexing systems that support ML pipelines.
*   **Foundation for Other Algorithms:** Some advanced data structures or algorithms used in ML (e.g., k-d trees for spatial partitioning, or even certain implementations of decision trees) might internally use balanced trees or benefit from their principles for efficient node management.
*   **Symbol Tables and Caching:** In complex ML frameworks or compilers that optimize ML code, AVL trees can be used for symbol tables (to store variable names, function definitions, etc.) or for implementing efficient caches where fast lookups and updates are necessary.
*   **Real-time Systems:** For ML applications requiring real-time responses, the guaranteed $O(\log n)$ performance of AVL trees is invaluable, as it prevents unexpected performance bottlenecks.

In essence, AVL trees provide a robust and efficient way to manage ordered data, which is a common requirement in the infrastructure supporting machine learning applications.

## How It Works
The fundamental principle of an AVL tree is to maintain balance. This is achieved by defining a **balance factor** for each node and performing **rotations** when this factor goes out of bounds.

### 1. Balance Factor
For any node in an AVL tree, its balance factor is defined as:
$BF(node) = \text{height}(\text{node.left}) - \text{height}(\text{node.right})$

The AVL property states that for every node in the tree, its balance factor must be one of $\{-1, 0, 1\}$.
*   A balance factor of 0 means the left and right subtrees have the same height.
*   A balance factor of 1 means the left subtree is one level taller than the right subtree.
*   A balance factor of -1 means the right subtree is one level taller than the left subtree.

If an insertion or deletion causes any node's balance factor to become 2 or -2, the tree is considered unbalanced at that node, and a rebalancing operation (rotation) is required.

### 2. Insertion
When a new node is inserted into an AVL tree, the process follows these steps:
1.  **Standard BST Insertion:** The new node is inserted as a leaf node, just like in a regular Binary Search Tree, based on its value.
2.  **Update Heights and Balance Factors:** After insertion, traverse back up the tree from the inserted node to the root. For each node on this path:
    *   Recalculate its height (which is $1 + \max(\text{height}(\text{left child}), \text{height}(\text{right child}))$).
    *   Recalculate its balance factor.
3.  **Check for Imbalance and Rebalance:** If, during the upward traversal, a node is found whose balance factor is $\{-2, 2\}$, it means the AVL property is violated. This is the "critical node" or "pivot node." At this point, one or more rotations are performed to restore balance. There are four types of rotations, categorized by the imbalance pattern.

### 3. Rotations
Rotations are local operations that rearrange a small portion of the tree to restore balance without violating the BST property (i.e., maintaining the order of elements).

#### a. Left Rotation (LL Imbalance)
*   **When:** Occurs when a node has a balance factor of -2 (right subtree is too tall), and the imbalance is caused by an insertion into the **right child's right subtree**. This is also called a "Right-Right" (RR) case.
*   **How:** The right child of the unbalanced node becomes the new parent. The unbalanced node becomes the left child of the new parent. Any left child of the new parent (that was previously there) becomes the right child of the old parent.
    ```
        A (-2)             B (0)
         \                / \
          B (new node)   A   C
           \
            C
    ```
    (A is unbalanced, B is A's right child, C is B's right child)

#### b. Right Rotation (RR Imbalance)
*   **When:** Occurs when a node has a balance factor of 2 (left subtree is too tall), and the imbalance is caused by an insertion into the **left child's left subtree**. This is also called a "Left-Left" (LL) case.
*   **How:** The left child of the unbalanced node becomes the new parent. The unbalanced node becomes the right child of the new parent. Any right child of the new parent (that was previously there) becomes the left child of the old parent.
    ```
          A (2)            B (0)
         /                / \
        B (new node)     C   A
       /
      C
    ```
    (A is unbalanced, B is A's left child, C is B's left child)

#### c. Left-Right Rotation (LR Imbalance)
*   **When:** Occurs when a node has a balance factor of 2 (left subtree is too tall), but the imbalance is caused by an insertion into the **left child's right subtree**. This is also called a "Left-Right" (LR) case.
*   **How:** This is a double rotation:
    1.  First, perform a **Left Rotation** on the left child of the unbalanced node. This transforms the LR case into an LL case.
    2.  Then, perform a **Right Rotation** on the original unbalanced node.
    ```
          A (2)             A (2)             C (0)
         /                 /                 / \
        B (-1)            C (1)             B   A
         \               /
          C             B
    ```
    (A is unbalanced, B is A's left child, C is B's right child)

#### d. Right-Left Rotation (RL Imbalance)
*   **When:** Occurs when a node has a balance factor of -2 (right subtree is too tall), but the imbalance is caused by an insertion into the **right child's left subtree**. This is also called a "Right-Left" (RL) case.
*   **How:** This is a double rotation:
    1.  First, perform a **Right Rotation** on the right child of the unbalanced node. This transforms the RL case into an RR case.
    2.  Then, perform a **Left Rotation** on the original unbalanced node.
    ```
        A (-2)            A (-2)            C (0)
         \                 \               / \
          B (1)             C (-1)        A   B
         /                   \
        C                     B
    ```
    (A is unbalanced, B is A's right child, C is B's left child)

### 4. Deletion
Deletion in an AVL tree is similar to insertion but can be more complex:
1.  **Standard BST Deletion:** First, perform the standard BST deletion. This might involve finding an in-order successor/predecessor if the node to be deleted has two children.
2.  **Update Heights and Balance Factors:** After deletion, traverse back up the tree from the parent of the deleted node (or the node that replaced it) to the root. For each node on this path:
    *   Recalculate its height.
    *   Recalculate its balance factor.
3.  **Check for Imbalance and Rebalance:** If any node's balance factor becomes $\{-2, 2\}$, perform the appropriate rotation(s). Unlike insertion, a single deletion might cause imbalances that propagate up the tree, requiring multiple rotations along the path to the root.

By consistently applying these rules, AVL trees guarantee that their height remains logarithmic, ensuring efficient operations.

## Mathematical Intuition
The core mathematical intuition behind AVL trees lies in proving that their height is always logarithmic with respect to the number of nodes, thus guaranteeing $O(\log n)$ time complexity for all operations.

Let $N_h$ be the minimum number of nodes in an AVL tree of height $h$.
*   For a height of 0, the tree has one node (the root). So, $N_0 = 1$.
*   For a height of 1, the tree must have at least two nodes (the root and one child). So, $N_1 = 2$.

For an AVL tree of height $h > 1$, to minimize the number of nodes while maintaining the AVL property, the root must have two children. One child's subtree must have height $h-1$, and the other child's subtree must have height $h-2$. This is because if both children had height $h-1$, the tree would have more nodes than necessary for height $h$. If one child had height less than $h-2$, the balance factor would be violated.

So, the recurrence relation for the minimum number of nodes $N_h$ in an AVL tree of height $h$ is:
$$N_h = 1 + N_{h-1} + N_{h-2}$$
This recurrence relation is very similar to the Fibonacci sequence ($F_n = F_{n-1} + F_{n-2}$).
The Fibonacci sequence starts $F_0=0, F_1=1, F_2=1, F_3=2, F_4=3, F_5=5, \dots$.
If we adjust the indices, we can see that $N_h$ grows approximately as fast as Fibonacci numbers.
Specifically, $N_h = F_{h+2} - 1$. (Some definitions might vary slightly, but the growth rate is the same).

The $k$-th Fibonacci number $F_k$ can be approximated by Binet's formula:
$$F_k \approx \frac{\phi^k}{\sqrt{5}}$$
where $\phi$ (phi) is the golden ratio, $\phi = \frac{1+\sqrt{5}}{2} \approx 1.618$.

Substituting this into our approximation for $N_h$:
$$N_h \approx \frac{\phi^{h+2}}{\sqrt{5}}$$
Now, we want to express $h$ in terms of $N_h$.
$$N_h \sqrt{5} \approx \phi^{h+2}$$
Taking the logarithm base $\phi$ on both sides:
$$\log_\phi (N_h \sqrt{5}) \approx h+2$$
$$h \approx \log_\phi (N_h \sqrt{5}) - 2$$
Since $\log_\phi (N_h \sqrt{5}) = \log_\phi N_h + \log_\phi \sqrt{5}$, and $\log_\phi \sqrt{5}$ is a constant, we can conclude that:
$$h = O(\log_\phi N_h)$$
Since $\phi$ is a constant greater than 1, $\log_\phi N_h$ is equivalent to $O(\log N_h)$ (any logarithmic base is equivalent to another by a constant factor).

This mathematical derivation proves that the height $h$ of an AVL tree with $N$ nodes is always proportional to $\log N$. This logarithmic height directly translates to the $O(\log n)$ time complexity for search, insertion, and deletion operations, as the number of nodes visited or operations performed (like rotations) is bounded by the height of the tree. The balance factor constraint of $\{-1, 0, 1\}$ is precisely what ensures this logarithmic height by preventing the tree from becoming skewed.

## Advantages
*   **Guaranteed $O(\log n)$ Time Complexity:** All fundamental operations (search, insertion, deletion) are guaranteed to complete in $O(\log n)$ time in the worst case. This is the primary advantage over regular BSTs.
*   **Predictable Performance:** Due to the guaranteed logarithmic height, AVL trees offer consistent and predictable performance, which is crucial for real-time systems and applications where performance guarantees are necessary.
*   **Efficient for Large Datasets:** The logarithmic time complexity makes AVL trees highly efficient for managing large volumes of data, as the number of operations grows very slowly with the size of the dataset.
*   **Good for In-Memory Databases and Symbol Tables:** Their efficiency in lookups and updates makes them suitable for applications like in-memory databases, dictionary implementations, and symbol tables in compilers.
*   **Self-Balancing:** The automatic rebalancing mechanism ensures that the tree structure remains optimal without manual intervention.

## Disadvantages
*   **Increased Complexity of Implementation:** AVL trees are significantly more complex to implement than regular BSTs due to the need to track heights/balance factors and perform rotations.
*   **Higher Constant Factors:** While the asymptotic time complexity is $O(\log n)$, the constant factors involved in operations are higher than those for a regular BST. This is because every insertion or deletion might require recalculating heights and balance factors along the path to the root, and potentially performing one or two rotations.
*   **More Memory Overhead:** Each node typically needs to store an additional piece of information (its height or balance factor), leading to slightly higher memory consumption per node compared to a simple BST.
*   **Frequent Rotations:** For applications with very frequent insertions and deletions, the overhead of performing rotations can be noticeable, potentially making other balanced trees (like Red-Black trees) a better choice in some scenarios.
*   **Not Cache-Friendly for Disk-Based Storage:** For data stored on disk, where I/O operations are expensive, AVL trees are not as cache-friendly as B-trees. B-trees are designed to minimize disk accesses by having a high branching factor, storing multiple keys per node, which is more suitable for disk-based databases.

## Real World Applications
1.  **Database Indexing:** AVL trees are used in database management systems to create indexes. An index allows for very fast retrieval of records based on a key, much faster than scanning the entire database. The $O(\log n)$ search time of AVL trees makes them ideal for this purpose, ensuring quick data access.
2.  **Symbol Tables in Compilers:** Compilers use symbol tables to store information about identifiers (variables, functions, classes) in a program, such as their names, types, and scopes. AVL trees can be used to implement these symbol tables, enabling quick lookups and updates of symbol information during the compilation process.
3.  **File Systems:** Some file systems or parts of them might use balanced trees to manage metadata, such as file names, directories, and their attributes. Efficient searching and updating of this metadata are crucial for file system performance.
4.  **Network Routers:** Routers often maintain large routing tables to determine the best path for data packets. AVL trees can be used to implement these routing tables, allowing for fast lookups of destination IP addresses to forward packets efficiently.
5.  **In-memory Data Structures:** Any application requiring a dynamic set or map data structure with guaranteed fast lookups, insertions, and deletions can benefit from AVL trees. Examples include dictionaries, sets, and priority queues in various software systems where data needs to be ordered and accessed quickly.

## Python Example

This Python example demonstrates the core functionality of an AVL tree: insertion, deletion, search, and maintaining balance through rotations. We'll create a simple `Node` class and an `AVLTree` class.

```python
import collections

class Node:
    """Represents a node in the AVL tree."""
    def __init__(self, key):
        self.key = key
        self.left = None
        self.right = None
        self.height = 1  # Height of the node (1 for a leaf)

class AVLTree:
    """Implements an AVL (Adelson-Velsky and Landis) self-balancing binary search tree."""

    def _get_height(self, node):
        """Helper to get the height of a node. Returns 0 if node is None."""
        if not node:
            return 0
        return node.height

    def _get_balance(self, node):
        """Helper to get the balance factor of a node."""
        if not node:
            return 0
        return self._get_height(node.left) - self._get_height(node.right)

    def _right_rotate(self, y):
        """Performs a right rotation around node y."""
        x = y.left
        T2 = x.right

        # Perform rotation
        x.right = y
        y.left = T2

        # Update heights
        y.height = 1 + max(self._get_height(y.left), self._get_height(y.right))
        x.height = 1 + max(self._get_height(x.left), self._get_height(x.right))

        return x # Return new root of the subtree

    def _left_rotate(self, x):
        """Performs a left rotation around node x."""
        y = x.right
        T2 = y.left

        # Perform rotation
        y.left = x
        x.right = T2

        # Update heights
        x.height = 1 + max(self._get_height(x.left), self._get_height(x.right))
        y.height = 1 + max(self._get_height(y.left), self._get_height(y.right))

        return y # Return new root of the subtree

    def insert(self, root, key):
        """Inserts a key into the AVL tree and rebalances it."""
        # 1. Perform standard BST insertion
        if not root:
            return Node(key)
        elif key < root.key:
            root.left = self.insert(root.left, key)
        else:
            root.right = self.insert(root.right, key)

        # 2. Update height of the current node
        root.height = 1 + max(self._get_height(root.left), self._get_height(root.right))

        # 3. Get the balance factor
        balance = self._get_balance(root)

        # 4. If the node is unbalanced, perform rotations

        # Left Left Case (LL)
        if balance > 1 and key < root.left.key:
            print(f"  Rebalancing (LL) at node {root.key} for key {key}")
            return self._right_rotate(root)

        # Right Right Case (RR)
        if balance < -1 and key > root.right.key:
            print(f"  Rebalancing (RR) at node {root.key} for key {key}")
            return self._left_rotate(root)

        # Left Right Case (LR)
        if balance > 1 and key > root.left.key:
            print(f"  Rebalancing (LR) at node {root.key} for key {key}")
            root.left = self._left_rotate(root.left)
            return self._right_rotate(root)

        # Right Left Case (RL)
        if balance < -1 and key < root.right.key:
            print(f"  Rebalancing (RL) at node {root.key} for key {key}")
            root.right = self._right_rotate(root.right)
            return self._left_rotate(root)

        return root

    def _get_min_value_node(self, node):
        """Helper to find the node with the minimum key value in a subtree."""
        if node is None or node.left is None:
            return node
        return self._get_min_value_node(node.left)

    def delete(self, root, key):
        """Deletes a key from the AVL tree and rebalances it."""
        # 1. Perform standard BST deletion
        if not root:
            return root

        if key < root.key:
            root.left = self.delete(root.left, key)
        elif key > root.key:
            root.right = self.delete(root.right, key)
        else: # Key is found
            # Node with only one child or no child
            if root.left is None:
                temp = root.right
                root = None
                return temp
            elif root.right is None:
                temp = root.left
                root = None
                return temp

            # Node with two children: Get the in-order successor (smallest in the right subtree)
            temp = self._get_min_value_node(root.right)
            root.key = temp.key # Copy the successor's data to this node
            root.right = self.delete(root.right, temp.key) # Delete the successor

        if root is None:
            return root

        # 2. Update height of the current node
        root.height = 1 + max(self._get_height(root.left), self._get_height(root.right))

        # 3. Get the balance factor
        balance = self._get_balance(root)

        # 4. If the node is unbalanced, perform rotations (same as insert, but check all 4 cases)

        # Left Left Case (LL)
        if balance > 1 and self._get_balance(root.left) >= 0: # >=0 covers LL and LR after deletion
            print(f"  Rebalancing (LL) after deleting key {key} at node {root.key}")
            return self._right_rotate(root)

        # Left Right Case (LR)
        if balance > 1 and self._get_balance(root.left) < 0:
            print(f"  Rebalancing (LR) after deleting key {key} at node {root.key}")
            root.left = self._left_rotate(root.left)
            return self._right_rotate(root)

        # Right Right Case (RR)
        if balance < -1 and self._get_balance(root.right) <= 0: # <=0 covers RR and RL after deletion
            print(f"  Rebalancing (RR) after deleting key {key} at node {root.key}")
            return self._left_rotate(root)

        # Right Left Case (RL)
        if balance < -1 and self._get_balance(root.right) > 0:
            print(f"  Rebalancing (RL) after deleting key {key} at node {root.key}")
            root.right = self._right_rotate(root.right)
            return self._left_rotate(root)

        return root

    def search(self, root, key):
        """Searches for a key in the AVL tree."""
        if not root or root.key == key:
            return root
        if key < root.key:
            return self.search(root.left, key)
        return self.search(root.right, key)

    def inorder_traversal(self, root):
        """Performs an in-order traversal of the tree."""
        result = []
        if root:
            result.extend(self.inorder_traversal(root.left))
            result.append(root.key)
            result.extend(self.inorder_traversal(root.right))
        return result

    def print_tree_structure(self, root):
        """Prints the tree structure level by level (BFS)."""
        if not root:
            print("Tree is empty.")
            return

        nodes_at_level = collections.deque([(root, 0)]) # (node, level)
        current_level = 0
        level_output = []

        print("\nTree Structure (Level by Level):")
        while nodes_at_level:
            node, level = nodes_at_level.popleft()

            if level > current_level:
                print(f"Level {current_level}: {' '.join(level_output)}")
                level_output = []
                current_level = level

            node_info = f"{node.key}(H:{node.height},BF:{self._get_balance(node)})"
            level_output.append(node_info)

            if node.left:
                nodes_at_level.append((node.left, level + 1))
            if node.right:
                nodes_at_level.append((node.right, level + 1))
        
        print(f"Level {current_level}: {' '.join(level_output)}")


# --- Demonstration ---
if __name__ == "__main__":
    avl_tree = AVLTree()
    root = None
    
    # Dummy dataset for insertion
    keys_to_insert = [10, 20, 30, 40, 50, 25]
    print("--- Inserting elements ---")
    for key in keys_to_insert:
        print(f"Inserting {key}...")
        root = avl_tree.insert(root, key)
        avl_tree.print_tree_structure(root)
        print("-" * 30)

    print("\nIn-order traversal of the AVL tree:", avl_tree.inorder_traversal(root))
    print("Root of the tree:", root.key)

    # Demonstrate search
    search_key = 30
    found_node = avl_tree.search(root, search_key)
    if found_node:
        print(f"\nSearching for {search_key}: Found {found_node.key}")
    else:
        print(f"\nSearching for {search_key}: Not found")

    search_key = 15
    found_node = avl_tree.search(root, search_key)
    if found_node:
        print(f"Searching for {search_key}: Found {found_node.key}")
    else:
        print(f"Searching for {search_key}: Not found")

    # Demonstrate deletion
    keys_to_delete = [20, 10]
    print("\n--- Deleting elements ---")
    for key in keys_to_delete:
        print(f"Deleting {key}...")
        root = avl_tree.delete(root, key)
        avl_tree.print_tree_structure(root)
        print("-" * 30)

    print("\nFinal in-order traversal of the AVL tree:", avl_tree.inorder_traversal(root))
    if root:
        print("New root of the tree:", root.key)
    else:
        print("Tree is empty.")

    # Example of a more complex deletion that might trigger multiple rebalances
    print("\n--- Inserting more elements for complex deletion test ---")
    root = None
    complex_keys = [9, 5, 10, 0, 6, 11, -1, 1, 2]
    for key in complex_keys:
        root = avl_tree.insert(root, key)
    avl_tree.print_tree_structure(root)
    print("\nIn-order traversal:", avl_tree.inorder_traversal(root))

    print("\n--- Deleting 10 (might trigger rebalance) ---")
    root = avl_tree.delete(root, 10)
    avl_tree.print_tree_structure(root)
    print("\nIn-order traversal:", avl_tree.inorder_traversal(root))
```

**Explanation of the Python Code:**

1.  **`Node` Class:** Represents a single node in the AVL tree, storing its `key`, references to its `left` and `right` children, and its `height`. The height is crucial for calculating the balance factor.
2.  **`AVLTree` Class:**
    *   **`_get_height(node)`:** A helper function to safely get the height of a node (returns 0 for `None` nodes).
    *   **`_get_balance(node)`:** Calculates the balance factor of a node using the heights of its left and right subtrees.
    *   **`_right_rotate(y)` and `_left_rotate(x)`:** These are the core rotation functions. They take an unbalanced node (e.g., `y` for right rotation, `x` for left rotation), perform the necessary pointer changes to rotate the subtree, and then update the heights of the affected nodes. They return the new root of the rotated subtree.
    *   **`insert(root, key)`:**
        *   First, it performs a standard recursive BST insertion.
        *   After insertion, it updates the `height` of the current `root` node.
        *   It then calculates the `balance` factor.
        *   Based on the `balance` factor and the `key` being inserted (to determine if it's an LL, RR, LR, or RL case), it calls the appropriate rotation function(s).
        *   It returns the (potentially new) root of the subtree.
    *   **`_get_min_value_node(node)`:** A helper for deletion, finding the node with the smallest key in a given subtree (used to find the in-order successor).
    *   **`delete(root, key)`:**
        *   Performs a standard recursive BST deletion.
        *   Handles cases for nodes with 0, 1, or 2 children.
        *   After deletion, it updates the `height` and `balance` factor of the current `root` node.
        *   Similar to insertion, it checks the balance factor and performs rotations if an imbalance is detected. The conditions for deletion are slightly more general (e.g., `_get_balance(root.left) >= 0` for LL case) because deletion can cause different types of imbalances than insertion.
        *   It returns the (potentially new) root of the subtree.
    *   **`search(root, key)`:** A standard recursive BST search function.
    *   **`inorder_traversal(root)`:** Performs an in-order traversal to print the sorted keys in the tree, useful for verification.
    *   **`print_tree_structure(root)`:** A utility function to visualize the tree level by level, showing each node's key, height, and balance factor. This helps in understanding how the tree balances itself.

The `if __name__ == "__main__":` block demonstrates the usage by inserting a sequence of numbers, printing the tree structure after each insertion (and any rebalancing), performing searches, and then demonstrating deletions.

## Interview Questions

1.  **What is an AVL tree? How does it differ from a regular Binary Search Tree (BST)?**
    *   **Answer:** An AVL tree is a self-balancing Binary Search Tree. It maintains a property that for every node, the height difference between its left and right subtrees (called the balance factor) must be -1, 0, or 1. If this property is violated after an insertion or deletion, the tree performs rotations to restore balance.
    *   The key difference from a regular BST is this self-balancing mechanism. A regular BST can become skewed (like a linked list) in the worst case, leading to $O(n)$ time complexity for operations. An AVL tree guarantees $O(\log n)$ time complexity for all operations by preventing such skewness.

2.  **What is the balance factor in an AVL tree, and what are its allowed values?**
    *   **Answer:** The balance factor of a node in an AVL tree is defined as the height of its left subtree minus the height of its right subtree ($BF = H_{left} - H_{right}$). For a tree to be an AVL tree, the balance factor of every node must be -1, 0, or 1.

3.  **Explain the four types of rotations in an AVL tree. When is each applied?**
    *   **Answer:** Rotations are performed to restore balance when a node's balance factor becomes 2 or -2.
        *   **Left Rotation (RR case):** Applied when a node has a balance factor of -2 (right subtree too tall) and the imbalance is caused by an insertion into the right child's right subtree.
        *   **Right Rotation (LL case):** Applied when a node has a balance factor of 2 (left subtree too tall) and the imbalance is caused by an insertion into the left child's left subtree.
        *   **Left-Right Rotation (LR case):** A double rotation. Applied when a node has a balance factor of 2 (left subtree too tall) but the imbalance is caused by an insertion into the left child's right subtree. It involves a left rotation on the left child, followed by a right rotation on the original unbalanced node.
        *   **Right-Left Rotation (RL case):** A double rotation. Applied when a node has a balance factor of -2 (right subtree too tall) but the imbalance is caused by an insertion into the right child's left subtree. It involves a right rotation on the right child, followed by a left rotation on the original unbalanced node.

4.  **Why is an AVL tree preferred over a regular BST for large datasets?**
    *   **Answer:** For large datasets, the worst-case $O(n)$ performance of a regular BST can lead to severe performance degradation. An AVL tree guarantees $O(\log n)$ time complexity for all operations (search, insert, delete) by maintaining balance. This ensures predictable and efficient performance even with millions of elements, preventing the tree from becoming a bottleneck.

5.  **What is the time complexity of search, insertion, and deletion operations in an AVL tree? Justify it.**
    *   **Answer:** All three operations (search, insertion, deletion) have a worst-case time complexity of $O(\log n)$, where $n$ is the number of nodes.
    *   **Justification:** The AVL property ensures that the height of the tree is always logarithmic, $O(\log n)$. Since search involves traversing a path from the root to a leaf (or the target node), its complexity is directly proportional to the height. Insertion and deletion also involve traversing a path to find the insertion/deletion point, and then potentially traversing back up to the root to update heights and perform rotations. The number of rotations required after an insertion is at most two (one single or one double rotation), and after a deletion, it's at most $O(\log n)$ rotations (one for each node on the path to the root, though typically fewer). All these operations are bounded by the tree's height, hence $O(\log n)$.

6.  **Compare AVL trees with Red-Black trees.**
    *   **Answer:** Both AVL trees and Red-Black trees are self-balancing BSTs that guarantee $O(\log n)$ operations.
        *   **Balance Strictness:** AVL trees are more strictly balanced than Red-Black trees. AVL trees maintain a balance factor of $\{-1, 0, 1\}$, meaning the heights of subtrees differ by at most 1. Red-Black trees allow for a greater height difference (up to a factor of 2), but ensure balance by coloring nodes red or black and following specific rules (e.g., no two adjacent red nodes, paths from root to leaf have same number of black nodes).
        *   **Rotations:** AVL trees generally perform more rotations (or more complex double rotations) during insertion/deletion to maintain their stricter balance. Red-Black trees typically require fewer rotations on average.
        *   **Performance:** AVL trees offer slightly faster lookups (search) because they are more strictly balanced, leading to a shorter average path length. Red-Black trees have slightly faster insertions and deletions on average due to fewer rotations.
        *   **Implementation Complexity:** Both are complex, but Red-Black trees are often considered slightly easier to implement due to simpler rotation logic, though their rules can be tricky.
        *   **Use Cases:** AVL trees are preferred when read-heavy operations are dominant. Red-Black trees are often used in standard library implementations (e.g., `std::map` in C++, `TreeMap` in Java) because their amortized performance for mixed operations is often better, and they are slightly less rigid.

7.  **Can an AVL tree become completely unbalanced? Why or why not?**
    *   **Answer:** No, an AVL tree cannot become completely unbalanced. The fundamental property of an AVL tree is its self-balancing mechanism. After every insertion or deletion, the tree checks the balance factor of affected nodes. If any node's balance factor deviates from $\{-1, 0, 1\}$, rotations are immediately performed to restore balance. This continuous rebalancing ensures that the height of the tree always remains logarithmic, preventing it from ever degrading into a skewed, unbalanced structure.

8.  **Describe the steps for inserting a node into an AVL tree.**
    *   **Answer:**
        1.  Perform a standard BST insertion: Traverse the tree to find the correct leaf position and insert the new node.
        2.  Update heights: Traverse back up from the inserted node to the root, updating the height of each node on the path.
        3.  Check balance factors: For each node on the path, calculate its balance factor.
        4.  Rebalance if necessary: If a node's balance factor becomes 2 or -2, perform the appropriate rotation(s) (LL, RR, LR, or RL) to restore balance. This rebalancing might change the subtree root, so the parent's pointer needs to be updated.

9.  **Describe the steps for deleting a node from an AVL tree.**
    *   **Answer:**
        1.  Perform a standard BST deletion:
            *   If the node is a leaf, simply remove it.
            *   If it has one child, replace it with its child.
            *   If it has two children, find its in-order successor (smallest node in the right subtree), copy the successor's key to the node being deleted, and then recursively delete the successor.
        2.  Update heights: Traverse back up from the parent of the deleted node (or the node that replaced it) to the root, updating the height of each node on the path.
        3.  Check balance factors: For each node on the path, calculate its balance factor.
        4.  Rebalance if necessary: If a node's balance factor becomes 2 or -2, perform the appropriate rotation(s). Unlike insertion, deletion might require multiple rotations as imbalances can propagate further up the tree.

10. **What is the space complexity of an AVL tree?**
    *   **Answer:** The space complexity of an AVL tree is $O(n)$, where $n$ is the number of nodes. Each node stores its key, pointers to its left and right children, and its height (or balance factor). Therefore, the space required grows linearly with the number of nodes in the tree.

    *   **Explanation:** A balance factor of 2 means the left subtree is too tall. If the left child also has a positive balance factor (or 0), it implies the imbalance is on the left child's left side (LL case), which is resolved by a single Right Rotation.
