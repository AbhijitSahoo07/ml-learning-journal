# Hash Tables

## Overview
Imagine you have a massive collection of items, like a library full of books, and you want to find a specific book very, very quickly. If the books are just piled up randomly, finding one would take ages. If they're sorted alphabetically, it's faster, but still involves some searching. What if you could instantly go to the exact shelf and spot where your book is supposed to be? That's essentially what a **Hash Table** (also known as a Hash Map or Dictionary) does for data.

A hash table is a powerful data structure that stores data in key-value pairs. Its primary goal is to allow for extremely fast (ideally, constant time) average-case lookups, insertions, and deletions. It achieves this by using a special function called a **hash function** to transform each key into an index, which then points to a specific location (or "bucket") in an underlying array where the corresponding value is stored. Think of it like a super-efficient indexing system for your data.

## What Problem It Solves
Hash tables are designed to solve the problem of inefficient data retrieval and storage when you need quick access to items based on a unique identifier (a key).

Here's a breakdown of the core problems it addresses:

1.  **Slow Search in Unordered Data**: If you have a simple list or array of items and you want to find a specific item, you might have to check every single item until you find it. In the worst case, this takes $O(N)$ time, where $N$ is the number of items. For large datasets, this is unacceptably slow.

2.  **Limited Key Types**: Traditional arrays use integer indices. What if you want to look up data using a string (like a person's name) or an object as a key? Hash tables provide a way to map these complex keys to integer indices.

3.  **Inefficient Key-Value Storage**: While data structures like balanced binary search trees offer $O(\log N)$ time complexity for search, insertion, and deletion, hash tables aim for an even faster $O(1)$ average-case performance. This difference becomes significant for very large datasets where even logarithmic time can be too slow.

**Why is it needed in machine learning?**

Hash tables are incredibly useful in machine learning for several reasons:

*   **Feature Engineering (e.g., Feature Hashing)**: In ML, especially with text data or categorical features, you often encounter a vast number of unique features (e.g., words in a vocabulary, unique categories). One-hot encoding these can lead to extremely high-dimensional sparse vectors. Feature hashing (or the "hashing trick") uses a hash function to map these high-dimensional features into a lower-dimensional space, reducing memory usage and computation without explicitly storing the mapping. This is particularly useful when the number of unique features is too large to fit in memory.
*   **Counting Occurrences**: When processing text (Natural Language Processing), you often need to count the frequency of words or n-grams. Hash tables (like Python's `dict`) are perfect for this, allowing you to quickly increment counts for each unique word encountered.
*   **Caching**: In complex ML pipelines, certain computations or model predictions might be expensive but frequently requested for the same input. Hash tables can be used to cache these results, storing `(input_data_hash, prediction)` pairs for quick retrieval, avoiding redundant computations.
*   **Implementing Sets**: Sets, which store unique items, are often implemented using hash tables internally, leveraging their fast lookup capabilities to check for item existence.

## How It Works
The magic of a hash table lies in its ability to quickly convert a key into an array index. Let's break down the step-by-step mechanism:

1.  **Key-Value Pairs**: Data is always stored as a pair: a `key` and its associated `value`. The `key` is what you use to look up the `value`. Keys must be unique and typically immutable (like strings, numbers, or tuples) so their hash value doesn't change.

2.  **The Hash Function**:
    *   When you want to store a `(key, value)` pair, the `key` is first passed through a special function called a **hash function**.
    *   A hash function takes an input (the key) and returns a fixed-size integer, known as the **hash code** or **hash value**.
    *   **Properties of a good hash function**:
        *   **Deterministic**: The same key must always produce the same hash code.
        *   **Fast**: It should compute the hash code quickly.
        *   **Uniform Distribution**: It should distribute keys as evenly as possible across the range of possible hash codes to minimize collisions.
        *   **Sensitive to Input Changes**: Even a small change in the key should result in a significantly different hash code.

3.  **Index Calculation (Mapping to Array Index)**:
    *   The hash code generated by the hash function is often a very large integer. To map this hash code to a valid index within the underlying array (which has a fixed size, say $M$), we typically use the **modulo operator** (`%`).
    *   The formula is: `index = hash_code % M`.
    *   This ensures that the calculated `index` always falls within the bounds of the array (from $0$ to $M-1$).

4.  **Storage (Buckets)**:
    *   The underlying data structure of a hash table is usually a simple array, often called the "bucket array" or "hash table array."
    *   Once the `index` is calculated, the `value` (or the `key-value` pair itself) is stored at that specific `index` in the bucket array. Each slot in this array is called a "bucket."

5.  **Collision Handling**:
    *   It's possible, and even probable, that two different keys might produce the same hash code, or map to the same array index after the modulo operation. This is called a **collision**.
    *   Collisions are inevitable, especially with a finite-sized array and an infinite number of possible keys. How a hash table deals with collisions is crucial for its performance.
    *   There are two main strategies for collision handling:

        *   **a) Chaining**:
            *   Each bucket in the hash table array doesn't just store a single value; instead, it stores a pointer to a **linked list** (or another data structure like a small array or balanced tree).
            *   When a collision occurs, the new key-value pair is simply added to the linked list at the calculated index.
            *   To retrieve an item, you hash the key, go to the corresponding bucket, and then traverse the linked list to find the correct key-value pair.

        *   **b) Open Addressing**:
            *   Instead of storing multiple items at the same index, open addressing searches for the *next available empty slot* in the array when a collision occurs.
            *   **Probing**: The process of searching for an empty slot is called probing.
            *   **Linear Probing**: If `index` is occupied, try `(index + 1) % M`, then `(index + 2) % M`, and so on, until an empty slot is found. This can lead to "primary clustering," where long runs of occupied slots form, slowing down searches.
            *   **Quadratic Probing**: If `index` is occupied, try `(index + 1^2) % M`, then `(index + 2^2) % M`, etc. This helps mitigate primary clustering but can lead to "secondary clustering."
            *   **Double Hashing**: Uses a second hash function to determine the step size for probing. If `index` is occupied, try `(index + h2(key)) % M`, then `(index + 2 * h2(key)) % M`, etc. This generally provides better distribution.

6.  **Retrieval**:
    *   To retrieve a value, you simply provide the `key`.
    *   The `key` is passed through the **same hash function** to get its `hash code`.
    *   The `hash code` is then mapped to an `index` using the **same modulo operation**.
    *   You go to that `index` in the bucket array.
    *   If using **chaining**, you traverse the linked list at that bucket, comparing keys until you find a match.
    *   If using **open addressing**, you start probing from that index, comparing keys until you find a match or an empty slot (indicating the key is not present).

## Mathematical Intuition
The mathematical foundation of hash tables revolves around mapping keys to indices and managing the distribution of these mappings.

1.  **Hash Function**:
    A hash function $h(key)$ takes an arbitrary key as input and produces an integer hash code.
    $$h: \text{Keys} \rightarrow \mathbb{Z}$$
    For example, a simple hash function for a string might sum the ASCII values of its characters. A more robust one would involve prime number multiplications and bit shifts to ensure better distribution.

2.  **Index Mapping**:
    The hash code is then mapped to an index within the hash table's underlying array. If the array has $M$ buckets (size $M$), the index is calculated using the modulo operator:
    $$index = h(key) \pmod M$$
    This ensures that the `index` is always in the range $[0, M-1]$. The choice of $M$ (often a prime number) can significantly impact collision rates.

3.  **Load Factor ($\alpha$)**:
    The **load factor** is a critical metric that measures how "full" the hash table is. It's defined as the ratio of the number of items stored ($N$) to the number of buckets ($M$):
    $$\alpha = \frac{N}{M}$$
    *   A low load factor ($\alpha < 1$) generally means fewer collisions and faster operations.
    *   A high load factor ($\alpha \ge 1$) means more collisions, leading to slower operations, especially with chaining (longer linked lists) or open addressing (more probes).
    *   When the load factor exceeds a certain threshold (e.g., 0.7 or 0.75), the hash table is typically **resized** (the underlying array $M$ is increased, usually doubled) and all existing items are **rehashed** into the new, larger table. This operation is expensive but ensures average-case performance remains good.

4.  **Time Complexity**:
    The efficiency of hash table operations (insertion, deletion, lookup) is usually discussed in terms of average-case and worst-case scenarios.

    *   **Average Case**: Assuming a good hash function that distributes keys uniformly and a low load factor, the average time complexity for all three operations is $O(1)$. This is because, on average, we expect to perform a constant number of operations (hash, modulo, and a few comparisons in a short linked list or a few probes).
        *   $T_{avg}(\text{insert}) = O(1)$
        *   $T_{avg}(\text{delete}) = O(1)$
        *   $T_{avg}(\text{lookup}) = O(1)$

    *   **Worst Case**: In the worst-case scenario, all keys might hash to the same bucket (due to a poor hash function or malicious input).
        *   If using **chaining**, this means all items are in a single linked list. Operations would then degenerate to traversing a linked list of $N$ items, resulting in $O(N)$ time.
        *   If using **open addressing**, this means probing through nearly all $N$ slots, also resulting in $O(N)$ time.
        *   $T_{worst}(\text{insert}) = O(N)$
        *   $T_{worst}(\text{delete}) = O(N)$
        *   $T_{worst}(\text{lookup}) = O(N)$

    The probability of a worst-case scenario is extremely low with well-designed hash functions and proper resizing strategies.

## Advantages
*   **Extremely Fast Average-Case Operations**: Provides $O(1)$ average-case time complexity for insertion, deletion, and lookup, making it one of the fastest data structures for these operations.
*   **Efficient for Large Datasets**: Its constant-time average performance scales very well with increasing data size, unlike arrays or linked lists which degrade linearly.
*   **Flexible Key Types**: Can use various data types (strings, objects, tuples) as keys, as long as they are hashable (immutable and provide a hash function).
*   **Memory Efficient (Relatively)**: While there's some overhead for the array and collision handling structures, it's generally more memory-efficient than tree-based structures for similar performance.
*   **Foundation for Other Structures**: Serves as the underlying implementation for many other data structures, such as sets and caches.

## Disadvantages
*   **Worst-Case Performance**: Can degrade to $O(N)$ time complexity in the worst-case scenario (e.g., all keys colliding), which is as bad as a linear scan. This is rare with good hash functions but a theoretical possibility.
*   **Space Overhead**: Requires extra space for the underlying array and potentially for linked lists (in chaining) or empty slots (in open addressing).
*   **Requires a Good Hash Function**: The performance heavily depends on the quality of the hash function. A poorly designed hash function leads to many collisions and degrades performance.
*   **Resizing is Expensive**: When the load factor becomes too high, the hash table needs to be resized (a new, larger array is allocated, and all existing items are rehashed). This is an $O(N)$ operation and can cause temporary performance spikes.
*   **Keys Must Be Hashable**: Keys must be immutable and provide a consistent hash value. Mutable objects (like lists in Python) cannot be directly used as keys because their hash value could change, breaking the lookup mechanism.
*   **No Inherent Ordering**: Hash tables do not maintain any specific order of elements. If you need sorted data, you'd have to sort the keys separately or use a different data structure (like a balanced binary search tree).

## Real World Applications
Hash tables are ubiquitous in computer science and have numerous practical applications:

1.  **Databases and Caching Systems**:
    *   **Database Indexing**: Databases use hash tables (or B-trees) to quickly locate records based on primary keys. When you query a database for a specific user ID, a hash table can map that ID directly to the disk location of the user's data.
    *   **Caches**: Web browsers, operating systems, and database systems use hash tables to implement caches. Frequently accessed data (e.g., web pages, file blocks, query results) are stored in a hash table for rapid retrieval, avoiding expensive re-computation or disk I/O.

2.  **Compilers and Interpreters (Symbol Tables)**:
    *   When a compiler or interpreter processes source code, it needs to keep track of all declared variables, functions, and their associated properties (type, scope, memory address). This mapping is stored in a **symbol table**, which is typically implemented using a hash table. This allows for very fast lookups of symbol information during compilation or execution.

3.  **Networking (Routers and Firewalls)**:
    *   **Routers**: Network routers use hash tables to store routing tables, mapping IP addresses to network interfaces. This enables them to quickly determine the next hop for data packets.
    *   **Firewalls**: Firewalls use hash tables to store rules for filtering network traffic (e.g., blocking specific IP addresses or ports), allowing for fast decision-making on whether to permit or deny a connection.

4.  **Machine Learning (Feature Hashing, NLP)**:
    *   **Feature Hashing (Hashing Trick)**: As mentioned, in ML, especially with high-dimensional sparse data (like text features), feature hashing maps features (e.g., words, n-grams) to a fixed-size vector using a hash function. This reduces memory footprint and computational cost without storing a full vocabulary mapping.
    *   **Natural Language Processing (NLP)**: Hash tables are fundamental for tasks like counting word frequencies, building inverted indices for search engines, and storing dictionaries or vocabularies for text processing. Python's `dict` is heavily used for these purposes.

5.  **Cryptography (Cryptographic Hash Functions)**:
    *   While not directly a "hash table" in the data structure sense, the underlying concept of a hash function is critical in cryptography. Cryptographic hash functions (like SHA-256) produce a fixed-size "fingerprint" of data. These are used for data integrity checks, digital signatures, and password storage (storing hash of password instead of plain text).

## Python Example
Python's built-in `dict` type is an excellent example of a highly optimized hash table. However, to illustrate the underlying mechanics, let's implement a simplified custom hash table using chaining for collision resolution.

```python
import hashlib # For a more robust hash function than built-in hash()

class SimpleHashTable:
    """
    A simple custom hash table implementation using chaining for collision resolution.
    """
    def __init__(self, capacity=10):
        """
        Initializes the hash table with a given capacity.
        Each bucket will be a list to handle collisions (chaining).
        """
        self.capacity = capacity
        self.buckets = [[] for _ in range(self.capacity)]
        self.size = 0 # Number of key-value pairs stored

    def _get_hash_index(self, key):
        """
        Computes a hash index for a given key.
        Uses SHA-256 for a more robust hash, then modulo by capacity.
        """
        # Ensure key is bytes for hashlib
        if isinstance(key, str):
            key_bytes = key.encode('utf-8')
        else:
            key_bytes = str(key).encode('utf-8')

        # Use SHA-256 hash, then convert to int and take modulo
        hash_digest = hashlib.sha256(key_bytes).hexdigest()
        hash_int = int(hash_digest, 16) # Convert hex string to integer
        return hash_int % self.capacity

    def insert(self, key, value):
        """
        Inserts a key-value pair into the hash table.
        Handles collisions using chaining.
        """
        index = self._get_hash_index(key)
        bucket = self.buckets[index]

        # Check if key already exists in the bucket (update value)
        for i, (existing_key, existing_value) in enumerate(bucket):
            if existing_key == key:
                bucket[i] = (key, value) # Update existing value
                print(f"Updated key '{key}' at index {index}.")
                return

        # If key not found, add new key-value pair to the bucket
        bucket.append((key, value))
        self.size += 1
        print(f"Inserted ('{key}', '{value}') at index {index}.")

        # Optional: Resize if load factor gets too high (simplified for this example)
        # if self.size / self.capacity > 0.7:
        #     self._resize()

    def get(self, key):
        """
        Retrieves the value associated with a given key.
        Returns None if the key is not found.
        """
        index = self._get_hash_index(key)
        bucket = self.buckets[index]

        for existing_key, value in bucket:
            if existing_key == key:
                print(f"Retrieved value for key '{key}': '{value}' from index {index}.")
                return value

        print(f"Key '{key}' not found.")
        return None

    def delete(self, key):
        """
        Deletes a key-value pair from the hash table.
        Returns True if deleted, False if key not found.
        """
        index = self._get_hash_index(key)
        bucket = self.buckets[index]

        for i, (existing_key, existing_value) in enumerate(bucket):
            if existing_key == key:
                del bucket[i]
                self.size -= 1
                print(f"Deleted key '{key}' from index {index}.")
                return True

        print(f"Key '{key}' not found for deletion.")
        return False

    def __len__(self):
        """Returns the number of items in the hash table."""
        return self.size

    def __str__(self):
        """String representation of the hash table."""
        items = []
        for i, bucket in enumerate(self.buckets):
            if bucket:
                items.append(f"Bucket {i}: {bucket}")
        return "\n".join(items) if items else "Hash Table is empty."

# --- Demonstration ---
print("--- Initializing Hash Table ---")
my_hash_table = SimpleHashTable(capacity=5) # Small capacity to easily demonstrate collisions

print("\n--- Inserting Data ---")
my_hash_table.insert("apple", 10)
my_hash_table.insert("banana", 20)
my_hash_table.insert("cherry", 30)
my_hash_table.insert("date", 40)
my_hash_table.insert("elderberry", 50) # This might cause a collision due to small capacity
my_hash_table.insert("fig", 60) # Another potential collision

print("\n--- Current Hash Table State ---")
print(my_hash_table)
print(f"Number of items: {len(my_hash_table)}")

print("\n--- Retrieving Data ---")
my_hash_table.get("banana")
my_hash_table.get("cherry")
my_hash_table.get("grape") # Non-existent key

print("\n--- Demonstrating Update ---")
my_hash_table.insert("apple", 100) # Update existing key
print(my_hash_table.get("apple"))

print("\n--- Demonstrating Collision (if any) ---")
# Let's manually check for keys that might collide with 'apple' or 'banana'
# This is hard to predict with SHA-256, but with a small capacity, it's likely.
# For example, if 'apple' hashes to index 0, and 'grape' also hashes to index 0,
# 'grape' would be added to the same list as 'apple'.
# Let's try inserting a key that we know will collide if capacity is small and hash is simple.
# With SHA-256, it's harder to force, but the mechanism is the same.
# The output will show if multiple items are in the same bucket.
my_hash_table.insert("lemon", 70)
my_hash_table.insert("mango", 80)
print("\n--- Hash Table State after more insertions ---")
print(my_hash_table)

print("\n--- Deleting Data ---")
my_hash_table.delete("banana")
my_hash_table.delete("grape") # Non-existent key for deletion

print("\n--- Final Hash Table State ---")
print(my_hash_table)
print(f"Number of items: {len(my_hash_table)}")

```

**Explanation of the Python Example:**

1.  **`SimpleHashTable` Class**:
    *   `__init__(self, capacity=10)`: Initializes the hash table. `capacity` defines the size of the underlying array (`self.buckets`). Each element in `self.buckets` is an empty list, which will hold `(key, value)` pairs for collision handling (chaining).
    *   `_get_hash_index(self, key)`: This is our custom hash function.
        *   It takes a `key` (can be string or other types).
        *   It converts the key to bytes (necessary for `hashlib`).
        *   It uses `hashlib.sha256` to generate a secure hash digest. This is more robust than Python's built-in `hash()` for demonstration purposes, as `hash()` can be non-deterministic across Python runs/versions.
        *   The hexadecimal hash digest is converted to an integer.
        *   Finally, the modulo operator (`% self.capacity`) maps this large integer to an index within the `0` to `capacity-1` range.
    *   `insert(self, key, value)`:
        *   Calculates the `index` using `_get_hash_index`.
        *   Accesses the `bucket` (the list) at that `index`.
        *   It iterates through the `bucket` to check if the `key` already exists. If it does, the `value` is updated.
        *   If the `key` is new, the `(key, value)` pair is appended to the `bucket` list, demonstrating chaining.
    *   `get(self, key)`:
        *   Calculates the `index`.
        *   Iterates through the `bucket` at that `index` to find the matching `key`.
        *   Returns the `value` if found, otherwise `None`.
    *   `delete(self, key)`:
        *   Calculates the `index`.
        *   Iterates through the `bucket` to find the `key`.
        *   If found, it removes the `(key, value)` pair from the list using `del bucket[i]`.
    *   `__len__` and `__str__`: Provide standard Pythonic ways to get the size and a readable representation of the hash table.

2.  **Demonstration**:
    *   We create a `SimpleHashTable` with a small `capacity` (5) to increase the likelihood of collisions and make the chaining visible.
    *   We insert several key-value pairs. The print statements show which index each item is inserted into. You'll observe that some keys might end up in the same bucket (e.g., `Bucket 0: [('apple', 100), ('lemon', 70)]`), demonstrating collision handling via chaining.
    *   We then retrieve, update, and delete items, showing how these operations work with the custom hash table.

This example clearly illustrates the core concepts of hashing, index mapping, and collision resolution using chaining.

## Interview Questions

Here are 10 relevant technical interview questions about Hash Tables, complete with comprehensive answers:

1.  **What is a Hash Table, and what is its primary purpose?**
    *   **Answer**: A hash table (or hash map) is a data structure that stores key-value pairs. Its primary purpose is to provide efficient (average $O(1)$ time complexity) storage and retrieval of data based on a key. It achieves this by using a hash function to map keys to indices in an underlying array, allowing for direct access to data.

2.  **Explain the core components of a Hash Table.**
    *   **Answer**: The core components are:
        *   **Key-Value Pairs**: The data elements stored, where each `key` is unique and maps to a `value`.
        *   **Hash Function**: A function that takes a `key` as input and converts it into an integer hash code. A good hash function is deterministic, fast, and distributes keys uniformly.
        *   **Hash Table Array (Buckets)**: An underlying array where the key-value pairs are stored. Each slot in this array is called a "bucket."
        *   **Collision Handling Mechanism**: A strategy to deal with situations where two different keys hash to the same index (a collision). Common methods include chaining and open addressing.

3.  **What is a hash collision, and how are collisions typically handled?**
    *   **Answer**: A hash collision occurs when two different keys, after being processed by the hash function and mapped to an array index, result in the same index. Since only one item can physically occupy a single array slot, a mechanism is needed to store multiple items at that index.
    *   Common handling strategies:
        *   **Chaining**: Each bucket in the hash table array stores a pointer to a linked list (or another data structure like a small array or balanced tree). When a collision occurs, the new key-value pair is simply added to the linked list at that index.
        *   **Open Addressing**: When a collision occurs, the hash table searches for the next available empty slot in the array using a probing sequence. Examples include Linear Probing (checking `index+1, index+2, ...`), Quadratic Probing (`index+1^2, index+2^2, ...`), and Double Hashing (using a second hash function to determine the step size).

4.  **What is the load factor in a Hash Table, and why is it important?**
    *   **Answer**: The load factor ($\alpha$) is the ratio of the number of items stored ($N$) to the number of buckets ($M$) in the hash table: $\alpha = N/M$. It's important because it indicates how "full" the hash table is and directly impacts its performance.
        *   A low load factor means fewer collisions and faster average-case operations.
        *   A high load factor means more collisions, leading to longer linked lists (in chaining) or more probes (in open addressing), which degrades performance towards $O(N)$.
        *   When the load factor exceeds a certain threshold (e.g., 0.7), the hash table is typically resized (its capacity $M$ is increased), and all existing items are rehashed to maintain good performance.

5.  **What are the average and worst-case time complexities for insertion, deletion, and lookup operations in a Hash Table?**
    *   **Answer**:
        *   **Average Case**: $O(1)$ for insertion, deletion, and lookup. This assumes a good hash function that distributes keys uniformly and a low load factor, minimizing collisions.
        *   **Worst Case**: $O(N)$ for insertion, deletion, and lookup. This occurs when all keys hash to the same bucket (due to a poor hash function or malicious input), effectively degenerating the hash table into a linked list (in chaining) or requiring a full scan (in open addressing).

6.  **When would you choose a Hash Table over a Balanced Binary Search Tree (BST) like an AVL tree or Red-Black tree?**
    *   **Answer**:
        *   **Choose Hash Table when**: You need the absolute fastest average-case performance ($O(1)$) for insertions, deletions, and lookups, and the order of elements is not important. Hash tables are excellent for implementing caches, symbol tables, and frequency counters.
        *   **Choose Balanced BST when**: You need guaranteed $O(\log N)$ worst-case performance for all operations, and/or you need to maintain elements in sorted order, perform range queries (e.g., find all keys between X and Y), or find the minimum/maximum element efficiently.

7.  **What makes a good hash function?**
    *   **Answer**: A good hash function should possess several key properties:
        *   **Deterministic**: The same key must always produce the same hash code.
        *   **Fast Computation**: It should be computationally inexpensive to calculate the hash code.
        *   **Uniform Distribution**: It should distribute keys as evenly as possible across the entire range of possible hash codes, minimizing collisions.
        *   **Sensitivity to Input Changes**: Even a small change in the key should result in a significantly different hash code (avalanche effect).
        *   **Low Collision Rate**: While collisions are inevitable, a good hash function minimizes their frequency.

8.  **Can mutable objects be used as keys in a Hash Table? Why or why not?**
    *   **Answer**: No, mutable objects (like Python lists or custom objects without proper `__hash__` and `__eq__` implementations) generally cannot be used as keys in a hash table.
    *   **Reason**: The hash table relies on the key's hash value to determine its storage location. If a key is mutable, its hash value could change after it has been inserted into the table. If the key is later modified, its original hash value would no longer map to its current location, making it impossible to retrieve the associated value. Keys must be immutable to ensure their hash value remains constant throughout their lifetime in the hash table.

9.  **Explain the concept of "Feature Hashing" (or the "Hashing Trick") in Machine Learning.**
    *   **Answer**: Feature Hashing is a technique used in machine learning, particularly with high-dimensional categorical or text features, to reduce dimensionality and memory usage. Instead of explicitly creating a mapping from each unique feature (e.g., a word) to a unique index (which can be very large), feature hashing uses a hash function to map features directly to indices in a fixed-size vector.
    *   A second hash function (or sign function) is often used to determine the sign of the feature's contribution to avoid destructive interference. This allows for a compact representation of features without storing a dictionary of all unique features, making it memory-efficient and scalable for very large vocabularies, though it introduces the possibility of hash collisions (different features mapping to the same index), which can slightly reduce model performance but is often acceptable for the memory/speed benefits.

10. **What are the main disadvantages of using Hash Tables?**
    *   **Answer**:
        *   **Worst-Case Performance**: Can degrade to $O(N)$ if all keys collide, though rare with good hash functions.
        *   **Space Overhead**: Requires extra memory for the underlying array and collision handling structures (linked lists or empty slots).
        *   **Requires a Good Hash Function**: Performance is highly dependent on the quality of the hash function; a poor one leads to many collisions.
        *   **Expensive Resizing**: When the load factor is exceeded, the table must be resized and all elements rehashed, which is an $O(N)$ operation.
        *   **No Inherent Ordering**: Elements are not stored in any particular order, so range queries or finding min/max elements are not efficient.
        *   **Keys Must Be Hashable**: Keys must be immutable to ensure consistent hash values.

5.  Why are mutable objects generally not suitable as keys in a Hash Table?
    A) They consume too much memory.
    B) Their values can change, making their hash code inconsistent and preventing retrieval.
    C) They cannot be compared for equality.
    D) Hash functions cannot process mutable data types.

### Answer Key

1.  **B) To provide fast average-case data retrieval, insertion, and deletion.**
    *   **Explanation**: The core strength of hash tables is their ability to perform these operations in near-constant time on average, making them highly efficient for quick data access.

2.  **C) Binary Search**
    *   **Explanation**: Chaining, Linear Probing, and Double Hashing are all standard techniques for resolving hash collisions. Binary search is an algorithm for finding an item in a sorted list or array, not a collision resolution strategy for hash tables.

3.  **C) $O(1)$**
    *   **Explanation**: In the average case, assuming a good hash function and proper load factor management, hash tables can retrieve an item in constant time, meaning the time taken does not significantly increase with the number of items.

4.  **B) 0.75**
    *   **Explanation**: The load factor is calculated as (Number of Items) / (Number of Buckets). So, $75 / 100 = 0.75$.

5.  **B) Their values can change, making their hash code inconsistent and preventing retrieval.**
    *   **Explanation**: A hash table relies on a key's hash code to determine its storage location. If a mutable key changes after insertion, its hash code will also change, meaning the hash table will no longer be able to find it at the original hashed location.
