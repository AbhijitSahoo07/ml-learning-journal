# Tries

## Overview
A Trie, also known as a Prefix Tree, is a specialized tree-like data structure used to store a dynamic set of strings or associative arrays where keys are strings. Unlike a binary search tree where nodes store keys, in a Trie, each node represents a common prefix of the strings stored in the tree. The path from the root to a node represents a prefix, and the node itself might mark the end of a complete word.

Imagine you have a dictionary of words. If you want to quickly find all words that start with "app", a Trie can do this incredibly efficiently. Each character of a word is stored as a separate node, and common prefixes share the same path from the root. This structure makes Tries exceptionally good for problems involving string prefixes, such as autocomplete features, spell checkers, and dictionary lookups. It's a fundamental data structure in computer science, particularly useful in areas like natural language processing (NLP) and search algorithms.

## What Problem It Solves
Tries primarily address the challenges associated with efficient storage and retrieval of strings, especially when dealing with operations involving prefixes. Here are the core problems it solves:

1.  **Inefficient String Search and Prefix Matching:** Traditional data structures like hash tables can check for the existence of a string in $O(L)$ time (where $L$ is the length of the string) on average. However, they don't efficiently support prefix-based searches (e.g., "find all words starting with 'auto'"). A Trie can perform both exact string searches and prefix searches in $O(L)$ time in the worst case, regardless of the number of strings stored.

2.  **Redundant Storage of String Prefixes:** When storing many words that share common prefixes (e.g., "apple", "apply", "application"), a simple list or array of strings would store these prefixes repeatedly. Tries optimize space by sharing common prefixes among different words. For instance, "app" would only be stored once and then branched out for "apple" and "apply".

3.  **Slow Autocomplete and Spell Checking:** In applications like search engines, text editors, or mobile keyboards, suggesting words as a user types (autocomplete) or identifying misspelled words requires rapid prefix matching. Tries provide the backbone for these features by allowing quick traversal to all words sharing a given prefix.

4.  **Lexicographical Ordering:** Tries naturally store words in a way that allows for easy retrieval in lexicographical (alphabetical) order, which can be beneficial for certain applications.

In machine learning, while Tries are not a "model" themselves, they are crucial data structures for preprocessing and feature engineering, especially in Natural Language Processing (NLP). For example:
*   **Tokenization and Dictionary Lookups:** When processing text, Tries can efficiently store and look up vocabulary words, stop words, or custom dictionaries.
*   **Feature Extraction:** Identifying specific n-grams or multi-word expressions as features can be accelerated using Tries.
*   **Search Query Autocomplete:** Powering the autocomplete functionality for search queries, which is often a front-end to ML-powered search ranking systems.

## How It Works
A Trie is essentially a tree where each node represents a character, and the path from the root to a node forms a prefix. Let's break down its components and operations:

### Core Components:
1.  **Root Node:** The starting point of the Trie. It typically doesn't represent any character itself, but acts as an empty prefix.
2.  **Trie Node:** Each node in the Trie has two main components:
    *   **Children:** A mapping (e.g., a dictionary or array) that links to other Trie nodes. The keys of this mapping are characters, and the values are the child nodes corresponding to those characters. For example, if a node represents the prefix "ap", its children might include a node for 'p' (leading to "app") or 'l' (leading to "apl").
    *   **`is_end_of_word` Flag:** A boolean flag that indicates whether the path from the root to this node constitutes a complete, valid word that was inserted into the Trie.

### Operations:

#### 1. Insertion (Adding a Word)
To insert a word into a Trie, you traverse the tree character by character:
*   Start at the root node.
*   For each character in the word:
    *   Check if the current node has a child corresponding to that character.
    *   If not, create a new Trie node for that character and add it as a child.
    *   Move to the child node.
*   Once all characters of the word have been processed, mark the final node as `is_end_of_word = True`.

**Example: Inserting "apple" and "apply"**
1.  **Insert "apple"**:
    *   Start at `root`.
    *   'a': `root` -> `a` (create 'a' node)
    *   'p': `a` -> `p` (create 'p' node)
    *   'p': `p` -> `p` (create 'p' node)
    *   'l': `p` -> `l` (create 'l' node)
    *   'e': `l` -> `e` (create 'e' node)
    *   Mark node 'e' as `is_end_of_word = True`.
2.  **Insert "apply"**:
    *   Start at `root`.
    *   'a': `root` -> `a` (node 'a' already exists, traverse)
    *   'p': `a` -> `p` (node 'p' already exists, traverse)
    *   'p': `p` -> `p` (node 'p' already exists, traverse)
    *   'l': `p` -> `l` (node 'l' already exists, traverse)
    *   'y': `l` -> `y` (create 'y' node)
    *   Mark node 'y' as `is_end_of_word = True`.

Notice how "appl" is a shared prefix between "apple" and "apply", and these characters are stored only once in the Trie.

#### 2. Search (Checking for a Word)
To search for a word, you follow a similar traversal:
*   Start at the root node.
*   For each character in the word:
    *   Check if the current node has a child corresponding to that character.
    *   If not, the word does not exist in the Trie; return `False`.
    *   If yes, move to the child node.
*   After traversing all characters, check if the final node is marked as `is_end_of_word = True`. If it is, the word exists; otherwise, it's just a prefix of another word, not a complete word itself.

**Example: Searching for "apple" and "app"**
*   **Search "apple"**: Traverse `root` -> `a` -> `p` -> `p` -> `l` -> `e`. Node 'e' is `is_end_of_word = True`. Result: `True`.
*   **Search "app"**: Traverse `root` -> `a` -> `p` -> `p`. Node 'p' (the third 'p') is NOT `is_end_of_word = True` (unless "app" was explicitly inserted). Result: `False` (if "app" wasn't inserted).

#### 3. Prefix Search (Checking for a Prefix)
To check if a given prefix exists in the Trie:
*   Start at the root node.
*   For each character in the prefix:
    *   Check if the current node has a child corresponding to that character.
    *   If not, the prefix does not exist; return `False`.
    *   If yes, move to the child node.
*   If you successfully traverse all characters of the prefix, then the prefix exists; return `True`. (The `is_end_of_word` flag is irrelevant for prefix existence).

## Mathematical Intuition

The mathematical intuition behind Tries primarily revolves around its efficiency in terms of time and space complexity, especially when dealing with string operations.

### Time Complexity

Let $L$ be the length of the string (word or prefix) being inserted or searched.
Let $N$ be the number of strings stored in the Trie.
Let $K$ be the size of the alphabet (e.g., 26 for lowercase English letters, 256 for ASCII characters).

*   **Insertion:** To insert a string of length $L$, we traverse at most $L$ nodes. At each node, we perform a constant number of operations (checking for a child, adding a child).
    *   Time Complexity: $O(L)$. This is highly efficient because it does not depend on the total number of strings $N$ in the Trie, only on the length of the string being inserted.

*   **Search (for a word):** Similar to insertion, we traverse at most $L$ nodes.
    *   Time Complexity: $O(L)$. Again, independent of $N$.

*   **Prefix Search (checking if a prefix exists):** Also involves traversing at most $L$ nodes (where $L$ is the length of the prefix).
    *   Time Complexity: $O(L)$.

*   **Finding all words with a given prefix:** This involves two steps:
    1.  Traverse to the node representing the end of the prefix ($O(L)$ time).
    2.  Perform a Depth-First Search (DFS) or Breadth-First Search (BFS) from that node to collect all words. If there are $M$ words with the given prefix and their average length is $L_{avg}$, this step could take $O(M \cdot L_{avg})$ in the worst case (visiting all nodes in the subtree).
    *   Total Time Complexity: $O(L + M \cdot L_{avg})$.

**Comparison with Hash Tables:**
For string search, a hash table typically offers $O(L)$ on average (due to hash function calculation and potential collisions). However, hash tables cannot efficiently perform prefix searches. To find all words with a prefix "pre", you'd have to iterate through all $N$ words in the hash table and check each one, leading to $O(N \cdot L)$ in the worst case. Tries offer a significant advantage here.

### Space Complexity

The space complexity of a Trie can be a trade-off.
*   In the worst case, if no two strings share any prefixes, a Trie might store each character of every string in a separate node. If there are $N$ strings, each of maximum length $L$, the total number of nodes could be up to $O(N \cdot L)$. Each node typically stores a map/dictionary of children (size $K$) and a boolean flag.
    *   Worst-case Space Complexity: $O(N \cdot L \cdot K)$ if each node's children map is sparsely populated and implemented as an array, or $O(N \cdot L)$ if implemented as a hash map where only existing children are stored.

*   In the best case, if all strings share very long common prefixes (e.g., "apple", "applet", "application"), the space usage is much more efficient. The total number of nodes is proportional to the sum of the lengths of all unique prefixes across all words.
    *   More accurately, the total number of nodes is bounded by the sum of the lengths of all words, $\sum_{i=1}^{N} L_i$, where $L_i$ is the length of the $i$-th word. Each node stores $K$ pointers (or a hash map).
    *   Space Complexity: $O(\sum_{i=1}^{N} L_i)$ in terms of nodes, or $O(\text{total number of characters in all words})$.

The key mathematical intuition is that Tries leverage **shared prefixes** to optimize both time and space. By structuring data based on character sequences, operations become proportional to the length of the string being processed, rather than the total number of strings. This makes them extremely efficient for dictionary-like operations and prefix-based searches.

## Advantages
*   **Fast Prefix Search:** Tries excel at finding all words with a given prefix. This is done in $O(L)$ time, where $L$ is the length of the prefix, regardless of the number of words in the Trie.
*   **Efficient Storage for Common Prefixes:** By sharing common prefixes among words, Tries can save significant space compared to storing words individually, especially in datasets with many words sharing initial characters (e.g., "apple", "apply", "application").
*   **Alphabetical Ordering:** Words stored in a Trie can be retrieved in lexicographical (alphabetical) order by performing a simple depth-first traversal.
*   **No Collisions:** Unlike hash tables, Tries do not suffer from key collisions, which can degrade performance.
*   **No Hash Function Calculation:** Tries do not require computing hash functions, which can sometimes be computationally expensive for long strings.
*   **Easy to Implement Autocomplete and Spell Checkers:** The structure naturally supports these features.

## Disadvantages
*   **High Space Complexity (Worst Case):** If the dataset contains many words with diverse prefixes (i.e., few shared prefixes), a Trie can consume a lot of memory. Each node typically needs to store pointers/references for all possible characters in the alphabet (e.g., 26 for English lowercase, 256 for ASCII), even if most are `None`.
*   **Memory Overhead per Node:** Each node requires memory for its children pointers (e.g., an array or dictionary) and the `is_end_of_word` flag. This overhead can be substantial for small alphabets or sparse data.
*   **Slower for Small Datasets:** For a very small number of words, a hash table might be faster due to simpler implementation and less overhead.
*   **Not Ideal for Arbitrary Pattern Matching:** Tries are optimized for prefix matching. They are not efficient for searching for patterns that appear in the middle or end of words, or for regular expression matching.
*   **Deletion Can Be Complex:** Deleting a word from a Trie requires careful handling to ensure that shared prefix nodes are not inadvertently removed if they are still part of other words. It often involves reference counting or recursive checks.

## Real World Applications
1.  **Autocomplete and Predictive Text:** This is perhaps the most common and intuitive application. When you type into a search bar (Google, Amazon), a text editor, or your phone's keyboard, Tries are often used behind the scenes to suggest possible completions for your input based on common prefixes. This significantly enhances user experience by speeding up typing and reducing errors.

2.  **Spell Checkers and Dictionaries:** Tries can efficiently store a dictionary of valid words. When a user types a word, the spell checker can quickly traverse the Trie to see if the word exists. If not, it can then use the Trie to find words with similar prefixes or small edits (e.g., one character difference) to suggest corrections.

3.  **IP Routing:** In networking, Tries (specifically a variant called "Radix Tries" or "Patricia Tries") are used to store IP routing tables. Network routers need to quickly determine the next hop for an incoming IP packet based on its destination IP address. IP addresses can be thought of as binary strings, and Tries allow for very fast longest-prefix matching to find the most specific route.

4.  **Browser History and URL Shorteners:** Browsers can use Tries to store and quickly search through your browsing history, suggesting previously visited URLs as you type. Similarly, some URL shortening services might use Tries to manage and look up short codes, ensuring uniqueness and fast retrieval.

5.  **Bioinformatics (Genomic Data Search):** In bioinformatics, Tries can be used to store and search for patterns in DNA or RNA sequences. These sequences are essentially long strings of characters (A, T, C, G), and Tries can efficiently find occurrences of specific genetic motifs or identify common subsequences.

## Python Example

This Python example demonstrates a basic Trie implementation, including insertion, searching for a word, and checking for a prefix.

```python
import collections

# 1. Define the TrieNode class
class TrieNode:
    def __init__(self):
        # A dictionary to store children nodes.
        # Keys are characters, values are TrieNode objects.
        self.children = collections.defaultdict(TrieNode)
        # A boolean flag to mark if this node represents the end of a complete word.
        self.is_end_of_word = False

# 2. Define the Trie class
class Trie:
    def __init__(self):
        # The root node of the Trie. It doesn't represent any character itself.
        self.root = TrieNode()

    def insert(self, word: str) -> None:
        """
        Inserts a word into the Trie.
        """
        current_node = self.root
        for char in word:
            # If the character is not a child of the current node,
            # defaultdict will automatically create a new TrieNode for it.
            current_node = current_node.children[char]
        # Mark the last node as the end of a complete word.
        current_node.is_end_of_word = True

    def search(self, word: str) -> bool:
        """
        Checks if a word exists in the Trie.
        """
        current_node = self.root
        for char in word:
            # If the character is not found, the word does not exist.
            if char not in current_node.children:
                return False
            current_node = current_node.children[char]
        # The word exists only if the final node is marked as an end of a word.
        return current_node.is_end_of_word

    def starts_with(self, prefix: str) -> bool:
        """
        Checks if there is any word in the Trie that starts with the given prefix.
        """
        current_node = self.root
        for char in prefix:
            # If the character is not found, no word starts with this prefix.
            if char not in current_node.children:
                return False
            current_node = current_node.children[char]
        # If we successfully traversed the entire prefix, then the prefix exists.
        return True

    def get_words_with_prefix(self, prefix: str) -> list[str]:
        """
        Retrieves all words in the Trie that start with the given prefix.
        """
        current_node = self.root
        # Traverse to the node representing the end of the prefix
        for char in prefix:
            if char not in current_node.children:
                return [] # No words start with this prefix
            current_node = current_node.children[char]

        # Now, perform a DFS from this prefix node to collect all words
        results = []
        def dfs(node, current_word):
            if node.is_end_of_word:
                results.append(current_word)
            for char, child_node in node.children.items():
                dfs(child_node, current_word + char)

        dfs(current_node, prefix)
        return results

# --- Demonstration ---
if __name__ == "__main__":
    # Create a Trie instance
    my_trie = Trie()

    # Dummy dataset of words
    words_to_insert = ["apple", "app", "apply", "apricot", "banana", "band", "bat", "cat", "car"]
    print(f"Inserting words: {words_to_insert}")

    # Fit the model/operation: Insert words into the Trie
    for word in words_to_insert:
        my_trie.insert(word)
    print("-" * 30)

    # Make predictions/results: Search for words
    print("Searching for words:")
    print(f"Is 'apple' in Trie? {my_trie.search('apple')}")       # Expected: True
    print(f"Is 'app' in Trie? {my_trie.search('app')}")           # Expected: True
    print(f"Is 'apply' in Trie? {my_trie.search('apply')}")       # Expected: True
    print(f"Is 'apricot' in Trie? {my_trie.search('apricot')}")   # Expected: True
    print(f"Is 'banana' in Trie? {my_trie.search('banana')}")     # Expected: True
    print(f"Is 'band' in Trie? {my_trie.search('band')}")         # Expected: True
    print(f"Is 'bat' in Trie? {my_trie.search('bat')}")           # Expected: True
    print(f"Is 'cat' in Trie? {my_trie.search('cat')}")           # Expected: True
    print(f"Is 'car' in Trie? {my_trie.search('car')}")           # Expected: True
    print(f"Is 'ap' in Trie? {my_trie.search('ap')}")             # Expected: False (only a prefix)
    print(f"Is 'application' in Trie? {my_trie.search('application')}") # Expected: False
    print(f"Is 'zebra' in Trie? {my_trie.search('zebra')}")       # Expected: False
    print("-" * 30)

    # Make predictions/results: Check for prefixes
    print("Checking for prefixes:")
    print(f"Does any word start with 'app'? {my_trie.starts_with('app')}")     # Expected: True
    print(f"Does any word start with 'ban'? {my_trie.starts_with('ban')}")     # Expected: True
    print(f"Does any word start with 'cat'? {my_trie.starts_with('cat')}")     # Expected: True
    print(f"Does any word start with 'appl'? {my_trie.starts_with('appl')}")   # Expected: True
    print(f"Does any word start with 'ze'? {my_trie.starts_with('ze')}")       # Expected: False
    print("-" * 30)

    # Make predictions/results: Get all words with a given prefix
    print("Getting words with prefixes:")
    print(f"Words starting with 'ap': {my_trie.get_words_with_prefix('ap')}") # Expected: ['apple', 'app', 'apply', 'apricot']
    print(f"Words starting with 'ban': {my_trie.get_words_with_prefix('ban')}") # Expected: ['banana', 'band']
    print(f"Words starting with 'c': {my_trie.get_words_with_prefix('c')}")   # Expected: ['cat', 'car']
    print(f"Words starting with 'z': {my_trie.get_words_with_prefix('z')}")   # Expected: []
    print(f"Words starting with 'apple': {my_trie.get_words_with_prefix('apple')}") # Expected: ['apple']
```

**Explanation of the Python Code:**

1.  **`TrieNode` Class:**
    *   `self.children`: A `collections.defaultdict(TrieNode)` is used. This is a convenient way to handle children. If you try to access `current_node.children[char]` and `char` is not yet a key, `defaultdict` automatically creates a new `TrieNode()` object for that key, making insertion cleaner.
    *   `self.is_end_of_word`: A boolean flag. `True` if the path to this node forms a complete word that was inserted, `False` otherwise.

2.  **`Trie` Class:**
    *   `self.root`: The starting point of our Trie, an instance of `TrieNode`.
    *   **`insert(self, word)`:**
        *   It iterates through each character of the `word`.
        *   For each character, it moves `current_node` to its child corresponding to that character. If the child doesn't exist, `defaultdict` creates it.
        *   After processing all characters, it sets `current_node.is_end_of_word = True` to mark the end of the inserted word.
    *   **`search(self, word)`:**
        *   It traverses the Trie character by character, similar to `insert`.
        *   If at any point a character is not found in `current_node.children`, it means the `word` does not exist, so it returns `False`.
        *   If the entire `word` is traversed, it then checks `current_node.is_end_of_word`. This is crucial because "app" might be a prefix of "apple", but "app" itself might not have been inserted as a complete word.
    *   **`starts_with(self, prefix)`:**
        *   This method is similar to `search`, but it only needs to successfully traverse all characters of the `prefix`. It doesn't care about the `is_end_of_word` flag of the final node, as long as the path exists.
    *   **`get_words_with_prefix(self, prefix)`:**
        *   First, it traverses to the node that represents the end of the `prefix`. If the prefix doesn't exist, it returns an empty list.
        *   Then, it uses a recursive Depth-First Search (`dfs`) helper function starting from that prefix node.
        *   The `dfs` function explores all paths downwards, building up `current_word` as it goes. When it encounters a node where `is_end_of_word` is `True`, it adds the `current_word` to the `results` list.

This example provides a clear and functional demonstration of how Tries work for common string operations.

## Interview Questions

1.  **What is a Trie, and what are its primary use cases?**
    *   **Answer:** A Trie (Prefix Tree) is a tree-like data structure used to store a dynamic set of strings. Each node represents a character, and paths from the root to nodes represent prefixes. Its primary use cases include autocomplete systems, spell checkers, dictionary lookups, IP routing, and bioinformatics for pattern matching in DNA sequences.

2.  **How does a Trie differ from a Binary Search Tree (BST) or a Hash Table for string storage?**
    *   **Answer:**
        *   **BST:** Stores entire strings in nodes and compares them lexicographically. Search time is $O(L \cdot \log N)$ where $L$ is string length and $N$ is number of strings. Does not efficiently support prefix searches.
        *   **Hash Table:** Stores strings as keys with $O(L)$ average time for insertion/search. Does not support prefix searches efficiently; requires iterating through all keys.
        *   **Trie:** Stores characters at nodes, sharing common prefixes. Insertion/search is $O(L)$, independent of $N$. Excellently supports prefix searches.

3.  **Explain the time complexity for insertion, search, and prefix search in a Trie.**
    *   **Answer:** For all three operations (insertion, searching for a word, or searching for a prefix), the time complexity is $O(L)$, where $L$ is the length of the string (word or prefix). This is because we traverse at most $L$ nodes, performing constant-time operations at each node. This complexity is independent of the total number of strings stored in the Trie.

4.  **What is the space complexity of a Trie? Discuss both best and worst-case scenarios.**
    *   **Answer:** The space complexity depends on the number of nodes and the size of the alphabet ($K$).
        *   **Worst Case:** If no two words share any prefixes, the Trie might store each character of every word in a distinct node. This could lead to $O(N \cdot L \cdot K)$ space, where $N$ is the number of words, $L$ is the maximum word length, and $K$ is the alphabet size (if using arrays for children). More accurately, it's $O(\sum L_i)$ total nodes, each with $K$ pointers.
        *   **Best Case:** If many words share long common prefixes, the space is optimized. The total number of nodes is proportional to the sum of the lengths of all unique prefixes across all words, which is generally much less than $N \cdot L$.

5.  **How would you implement a Trie node in Python?**
    *   **Answer:** A Trie node typically has two main components:
        1.  `children`: A dictionary (or hash map) where keys are characters and values are references to child Trie nodes. `collections.defaultdict(TrieNode)` is a common and efficient choice in Python.
        2.  `is_end_of_word`: A boolean flag, set to `True` if the path from the root to this node forms a complete word.

    ```python
    import collections
    class TrieNode:
        def __init__(self):
            self.children = collections.defaultdict(TrieNode)
            self.is_end_of_word = False
    ```

6.  **Describe the process of deleting a word from a Trie. What challenges does it present?**
    *   **Answer:** Deleting a word is more complex than insertion or search. You traverse the Trie to find the word. If found, you set its `is_end_of_word` flag to `False`. Then, you might need to prune unnecessary nodes. A node can be deleted if:
        1.  It's not the end of another word (`is_end_of_word` is `False`).
        2.  It has no other children (i.e., it's not a prefix for any other word).
    *   This often involves a recursive approach, starting from the last character of the word and moving upwards, deleting nodes as long as they meet the criteria. The challenge is to avoid deleting nodes that are still part of other valid words or prefixes.

7.  **When would you choose a Trie over a Hash Map for string storage?**
    *   **Answer:** Choose a Trie when:
        *   You need efficient prefix-based searches (e.g., autocomplete, finding all words starting with "abc").
        *   You want to store words in lexicographical order.
        *   You want to avoid hash collisions.
        *   You have a dataset with many words sharing common prefixes, leading to potential space savings.
    *   Choose a Hash Map when:
        *   You only need exact string lookups.
        *   Space is a critical concern and your strings don't share many prefixes.
        *   The dataset is small, where Trie overhead might be greater.

8.  **Can Tries be used for numerical data? If so, how?**
    *   **Answer:** Yes, Tries can be adapted for numerical data. You would convert numbers into strings (e.g., "123" becomes '1' -> '2' -> '3') or, more commonly, represent them in binary form. Each bit (0 or 1) would then be a child node. This is the basis for structures like Binary Tries or Radix Tries, which are used in IP routing tables for longest prefix matching on binary IP addresses.

9.  **What is a "compressed Trie" or "Radix Trie" (Patricia Trie), and why might it be used?**
    *   **Answer:** A compressed Trie (or Radix Trie/Patricia Trie) is an optimization of a standard Trie. It compresses paths that contain only single-child nodes into a single edge. Instead of each node representing a single character, an edge in a Radix Trie can represent a sequence of characters (a string). This reduces the number of nodes and memory usage, especially when there are many long, unbranched paths. It's used to save space and sometimes improve performance, particularly in applications like IP routing where long common prefixes are frequent.

10. **How would you find the longest common prefix among a set of strings using a Trie?**
    *   **Answer:**
        1.  Insert all strings into the Trie.
        2.  Start at the root. Traverse downwards.
        3.  At each node, check if it has more than one child, or if it marks the end of a word (`is_end_of_word = True`).
        4.  If either of these conditions is met, the path traversed so far is the longest common prefix. Stop and return the prefix.
        5.  If the node has only one child and is not the end of a word, continue traversing to that child, appending the character to the current prefix.
        *   This works because the longest common prefix will be the longest path from the root where all inserted words share the same character sequence. The path ends when a branch occurs or a word terminates.

5.  What is a potential disadvantage of Tries, especially for datasets with diverse strings?
    A) High risk of hash collisions.
    B) Inability to store words of varying lengths.
    C) Potentially high memory consumption due to node overhead.
    D) Slowest search time compared to other data structures.

---

### Answer Key

1.  **B) Guaranteed $O(1)$ time complexity for all operations.**
    *   **Explanation:** Trie operations (insertion, search) have a time complexity of $O(L)$, where $L$ is the length of the string, not $O(1)$. $O(1)$ would imply constant time regardless of string length, which is not true for Tries.

2.  **B) $O(L)$**
    *   **Explanation:** The search time in a Trie depends only on the length of the word being searched ($L$), as you traverse at most $L$ nodes. It does not depend on the total number of words ($N$) in the Trie.

3.  **D) A character, a boolean flag indicating end-of-word, and a map/dictionary of child nodes.**
    *   **Explanation:** Each node implicitly represents a character (by its position in the parent's children map). It explicitly stores a flag (`is_end_of_word`) and a collection of pointers/references to its children nodes, typically a map where keys are characters.

4.  **C) Autocomplete suggestions in search bars.**
    *   **Explanation:** Autocomplete systems are a classic application of Tries because they need to quickly find and suggest words based on the prefix a user has typed.

5.  **C) Potentially high memory consumption due to node overhead.**
    *   **Explanation:** If words do not share many common prefixes, a Trie can become very sparse, with many nodes having few children. Each node still requires memory for its children map (even if mostly empty) and the `is_end_of_word` flag, leading to significant memory overhead.
